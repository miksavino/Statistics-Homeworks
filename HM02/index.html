Homework 2 - From Wallet Seed to Ethereum Address: Hashing, Key Derivation and Cryptographic Primitives

Fundamental Cryptographic Distinctions

Key Generation vs. Key Derivation

According to NIST SP 800-57 Part 2 Rev. 1, key generation is defined as "the generation of a cryptographic key either as a single process using a random bit generator and an approved set of rules, or as created during key agreement or key derivation". As highlighted by IBM's Key Management guidelines, key generation represents the first stage of the cryptographic key lifecycle, establishing the security baseline on which all operations rely.

In contrast, according to NIST SP 800-57 Part 2 Rev. 1, key derivation is defined as "a process that derives new keying material from a key that is currently available".

Hence, while key generation creates the initial root entropy, key derivation structures that entropy into an arbitrary tree of keys without requiring new external randomness.

Public-Key Cryptography

Public-key cryptography relies on two separate keys: a public key, which can be shared openly, and a private key, which must remain secret.
Messages encrypted with the public key can only be decrypted with the corresponding private key, ensuring that only the intended recipient can access the information. Conversely, messages signed with a private key can be verified using the public key, providing authentication and integrity of the sender's identity and message content.

Hashing

Hashing is the process of converting data - text, numbers, files, or anything - into a fixed.length string of letters and numbers by using an algorithm called hash function (Codecademy - What Is Hashing, and How Does It Work?).

Hashing and encryption are both ways of transforming data:

  • Hashing is a one-way process, meaning that once the data is hashed, it cannot be changed back to its original form.
  • Encryption is a two-way process since encrypted data can be decrypted by someone with the correct key.

Checksums

According to NIST SP 800-12 Rev. 1, a checksum is "a value that is computed by a function that is dependent on the content of a data object and is stored or transmitted together with the object, for detecting changes in the data".
In other words, a checksum acts as a digital fingerprint: matching checksums mean the data is intact; mismatched checksums indicate integrity violations.

Encoding

According to Non-Human Identity Management Group - Encoding, encoding is a "reversible way of changing data into another representation, so it can be transported, stored or interpreted by another system.".
It is not a protection mechanism, but is about representation: an encoded value may look unreadable, but it is still the original data once decoded.

Standards and cryptographic primitives

BIP-39 (Mnemonic Sentence and Seed Generation)

BIP-39 is a standard that describes the process of generating mnemonic sentences for the creation of deterministic wallets. It aimes to simplify the process of wallet backup and recovery: by using a mnemonic sentence, users can restore their entire wallet, including all associated private keys, without needing to back up each key individually (TetherWiki - BIT-39).
BIP-39 operates by converting a randomly generated number into a sequence of words. This process involves several steps:

  • Generates raw random entropy of 128 to 256 bits.
  • Computes and appends an entropy-derived checksum to guarantee sentence integrity and detect transcription errors.
  • Splits the entropy-checksum pyaload into 11-bit segments, each indexing a word from a fixed 2048-words wordlist to form a mnemonic sentence (12 to 24 words).
  • Applies a key-stretching funtion to convert the sentence into a 512-bit binary seed, eliminating linguistic patterns.

BIP-32 (Hierarchical Deterministic Key Derivation)

BIP-32 introduces hierarchical deterministic wallets, allowing the derivation of a complete tree of keys from a single master binary seed (TetherWiki - BIT-32 and BIP-39).
The process of generating keys involves the following steps:

  • Uses the seed to derive a master private key and a 32-byte master chain code as the tree root.
  • Applies HMAC-SHA512 to combine the master key, the master chain code and a child index to recursively derive child keys. Each child key can be used to generate further child keys, creating a hierarchical structure.
Because HMAC acts as a PRF, each child key is computationally indistinguishable from keys sampled independently from a uniform distribution over the scalar field. Hence, without knowledge of the master chain code, observing multiple sibling child keys reveals zero statistical correlation between them.

BIP-44 (Standard Derivation Paths for Hierarchical Deterministic Wallets)

BIP-44 extends BIP-32 by defining a standard five-level derivation path to organize multi-account wallets deterministically from a single master seed, meaning that a single wallet can hold several different accounts. The derivation path has the following structure:
M / purpose' / coin_type' / account' / change / address_index

, where

  • M is the root node of the HD wallet.
  • purpose' is typically 44 and it indicates that the wallet is compatible with the BIP-44 standard.
  • coin_type' indicates the type of cryptocurrency (e.g., for Bitcoin, this number is 0).
  • account' indicates the wallet account number. Starting from 0, the number will be increased by 1 after creating a new account within the same wallet.
  • change indicates if the address is external (1) to receive funds or internal (0) to change address.
  • address_index indicated the account address number. It starts from 0 and it is increased by 1 after creating a new address within the same account.

Path levels marked with an apostrofo use hardened derivation, requiring the root private key, preventing root key recovery even if a child private key is compromised (SATOCHIP - Bitcoin Improvement Proposal #44 - BIP44).

secp256k1 (Elliptic-Curve Public-Key Cryptography)

secp256k1 is the elliptic curve cryptography standard used to generate private keys and create digital signaratures, allowing users to prove fund ownership without revealing their private keys.
The standard transforms a private key into a public key through elliptic curve multiplication: it multiplies the 256-bit private key scalar k by a predefined generator point G on the curve (Q = kG); the result is a 64-byte public key.
secp256k1 offers strong cryptographic security, efficient computation, relatively small key size, fast verification and low overhead (ECOS - secp256k1).

The security of the standard relies on the Elliptic Curve Logarithm Problem: deriving a public key from a private key is computationally easy; in contrast, deriving a private key from a public key is infeasible.
Hence, users can safely share public keys. However, scalar multiplication does not destroy algebraic relations: public keys alone do not exhibit bitwise independence or true avalanche properties.

Keccak-256 (Hash Function used in Ethereum Address Derivation)

Keccak-256 is a cryptographic hash function that maps arbitrary-length data onto a 256-bit fingerprint. It is designed to resist collision, pre-image and second pre-image attacks, meaning that is computationally infeasible to find two different inputs that produce the same hash or to reverse a hash back into its original data. These properties make Keccak-256 suitable for integrity checks, digital signatures, address generation and commitment schemes.
However, predictable, low-entropy or improperly encoded inputs can undermine security. Moreover, output hexadecimal string are difficult for humans to verify.
The hash function works using a two-phase sponge construction:

  • During the absorbing phase, pads and partitions input data into blocks, XORs them into a 1600-bit internal state and scrambles the state via the Kekkak-f permutation.
  • During the squeezing phase, extracts 256 bits from the internal state to produce the final hash (RugDoc - What Is the Kekkak-256 Algorithm? Complete Technical Guide).

In order to generate Ethereum addresses, the function keeps the last 20 bytes of the result.

EIP-55 (Ethereum mixed-case Checksum Address)

EIP-55 is a standard that defines a backward-compatible checksum for Ethereum addresses using mixed-case encoding. It prevents accidental loss of funds due to human typing errors or copy-paste corruptions without altering the 20-byte length address.

For each character in the address, if the corresponding bit in the hash is 1 and the character is a letter, it is capitalized. Otherwise it stays lowercase (Cryptools - EIP-55 Checksum).

SHA-2/SHA-512 vs Keccak-256 vs SHA-3

SHA-2 / SHA-512 are built on the Merkle–Damgård construction, used in legacy systems and to be safely deployed as a PRF or key derivation primitive, it requires wrapper construct such as HMAC and PBKDF2.
Since the internal state is exposed as the digest output, they suffer from length-extension attacks.

Kekkak-256 is built on the permutation-based sponge construction over a wide internal state divided into bitrate and capacity. Since the capacity bits are never exposed, the algorithm is immune to length-extension attacks.
It is used in modern designs and Ethereum to compress and hash the 64-byte public key into a 20-byte address.

SHA-3 represents the NIST standard based on the Keccak sponge architecture. While sharing the same underlying permutation as Keccak-256, it introduces distinct domain separation padding bytes (0x06 instead of 0x01). Consequently, official SHA-3 produces completely different digest outputs from Keccak-256 for identical inputs and is not compatible with Ethereum address derivation.

Why Ethereum Combines Heterogeneous Cryptographic Primitives

Ethereum does not rely on a single algorithm because no single cryptographic primitive can simultaneously satisfy the conflicting requirements of security, human usability, verification, and on-chain efficiency. Instead, it enforces a strict separation of concerns:

  • Human Usability vs. Machine Entropy → BIP-39 bridges this gap by encoding random entropy into a human-readable mnemonic wordlist and using PBKDF2 key stretching to prevent brute-force attacks.
  • Hierarchical Key Management vs. Static Storage → Instead of requiring a manual backup after every transaction, BIP-32 and BIP-44 use HMAC-SHA512 to deterministically derive an entire tree of multi-account keys from a single master seed.
  • Identity and Authorization vs. Irreversibility → Hash functions are one-way and cannot prove identity; secp256k1 provides asymmetric elliptic curve cryptography to authorize transactions without exposing the secret private key.
  • Breaking Algebraic Symmetries vs. Storage Efficiency → Elliptic curve multiplication preserves algebraic structures and exhibits geometric bias; Keccak-256 destroys these symmetries, providing a strict avalanche effect.
  • Error Detection vs. Backward Compatibility → Rather than altering address length with explicit checksum suffixes, EIP-55 embeds error detection into the casing of hexadecimal letters with zero byte overhead.
